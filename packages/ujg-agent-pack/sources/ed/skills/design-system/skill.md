## Core binding invariant

Graph nodes MUST NOT point directly to Design System artifacts.

Correct:

```text
Graph node <- Surface.graphNodeRef
Surface <- SurfaceRealization.surfaceRef
SurfaceRealization -> Component | Template
```

Never attach Components, Templates, Slots, SlotBindings, TokenSources, or realization metadata directly to Graph nodes.

## Review Graph and Surface before Design System

Before generating or reviewing Design System nodes:

1. inspect the relevant Graph topology;
2. inspect existing Surfaces and their `graphNodeRef`;
3. identify which Graph nodes actually have stable visible meaning;
4. distinguish visible interaction nodes from structural topology;
5. determine which visible boundary owns each nested affordance;
6. only then design SurfaceRealizations and presentation composition.

Do not use Components, Templates, Slots, or extra Surfaces to compensate for ambiguous or misleading Graph topology.

## Surface candidate filtering

Do not create a Surface mechanically for every Graph node.

For every potential Surface, apply this decision sequence.

### State or CompositeState candidate

Create a Surface when the node represents an independently meaningful visible experienced element that requires stable materialization, composition, identity, or observation.

Do not create a Surface merely because the State exists.

### Transition candidate

Ask in this order:

1. Does a requirement establish a distinct stable visible affordance for this Transition?

   * no -> do not create a Surface.
2. Is the Transition only a conditional outcome of one shared interaction?

   * yes -> do not create a Surface unless independently visible.
3. Is the Transition structural continuation across a journey/composite boundary?

   * yes -> do not create a Surface unless independently visible.
4. Otherwise, create a transition-backed Surface only when stable visible identity is genuinely required.

A transition label is not evidence of a button, link, CTA, menu item, control, or gesture target.

When correcting an existing document, delete unjustified transition-backed Surfaces. Do not merely leave them unrealized.

## Structural continuation

Transitions involving `JourneyExit`, `fromExitRef`, `JourneyEntry`, `toEntryRef`, or parent/child continuation require special care.

A visible interaction may occur inside a child journey while a parent transition only continues the resulting outcome.

Do not materialize both as the same visible action.

Rule:

> A Surface for an affordance MUST expose the Graph node that represents the actual local experienced interaction, not another transition that merely continues its result elsewhere in the topology.

If the local interaction already occurred, the continuation transition normally remains without a Surface.

## Conditional outcomes

A `ConditionalTransitionSet` represents condition-controlled alternative transitions, not automatically separate user actions.

For every transition referenced by a `ConditionalTransitionSet`:

```text
conditional membership
    ≠
visible affordance identity
```

Do not create one Surface per conditional branch merely because several transitions exist.

If one visible interaction resolves into several conditional transitions:

* represent the visible presentation as a Component when only presentation composition is needed;
* do not claim that Component identifies, triggers, or selects one Graph Transition;
* do not invent `Command`, `Intent`, action kinds, flags, or transition subtypes;
* do not mutate Graph topology merely to satisfy Design System composition;
* report an expressivity gap if stable interoperable identity for the shared interaction is required.

When reviewing an existing document, remove conditional-outcome Surfaces unless independent requirements justify their visibility.

## Ordinary user choices

Separate user choices may have separate transition-backed Surfaces when each choice has independently established visible identity.

Example distinction:

```text
choice A -> outcome A
choice B -> outcome B
```

may justify two visible affordances.

This is different from:

```text
one interaction
    ├── condition A -> outcome A
    └── condition B -> outcome B
```

which does not justify two action Surfaces by itself.

## Occurrence ownership

Before composing a child Surface, determine the nearest visible Graph node whose concrete occurrence owns that child affordance.

Compose the child Surface inside the realization of that owning Surface.

Do not skip an occurrence-owning visible boundary and bind its child affordance directly into an ancestor or aggregate Surface.

Use this principle for any repeated, nested, local, item-scoped, row-scoped, card-scoped, message-scoped, or similar interaction.

The rule is semantic, not layout-specific:

> Compose an affordance where its concrete occurrence belongs.

## Multi-instance State realization

`State.multiInstance` is Graph semantics.

Design System MUST NOT restate it through collection, repetition, cardinality, data-source, or instance-key vocabulary.

If a multi-instance State has stable visible occurrences, model:

```text
one authored State
one stable Surface
one SurfaceRealization
many concrete occurrences at runtime
```

Do not generate one Surface, Component, Template, SlotBinding, or realization per domain/runtime item.

A `targetSurfaceRef` to a Surface whose Graph node is multi-instance composes the stable Surface definition. It does not constrain occurrence count.

If independently modeled child Surfaces belong to each occurrence of a multi-instance State:

* the multi-instance State MUST have its own stable Surface;
* those child Surfaces MUST be composed into that State's Surface realization;
* do not hide the repeated visible boundary inside an opaque aggregate/list Component;
* do not move occurrence-local affordances into an ancestor/page-level realization.

This rule applies to any multi-occurrence visible element, regardless of domain.

## Aggregate and item boundaries

An aggregate Surface may compose an item Surface.

Prefer:

```text
aggregate Surface
    -> item Surface

item Surface
    -> item content Component
    -> item-local affordance Surface
```

over:

```text
aggregate Surface
    -> opaque collection Component
    -> item-local affordance Surface at aggregate level
```

when the Graph already models the item as a visible State with independent occurrence semantics.

Do not erase a meaningful Graph/Surface boundary by replacing it with a presentation-only Component.

## SurfaceRealization

Every `SurfaceRealization` MUST:

* reference exactly one Surface through `surfaceRef`;
* use exactly one of `componentRef` or `templateRef`.

Use `componentRef` for direct realization by one Component.

Use `templateRef` when reusable composition through Slots is required.

Do not use both.

Use `slotBindingRefs` only with `templateRef`.

A Surface that exists in the final interoperable model should normally have an intended realization in a Design System-complete artifact. An unrealized Surface is not an acceptable way to preserve a Surface that should have been removed.

## Component vs Template

Use the smallest artifact that preserves the meaningful presentation structure.

Use `Component` when one addressable design-system artifact directly realizes the Surface.

Use `Template` when the realization has reusable composition points.

Do not create a Template merely to wrap one Component.

Do not collapse a meaningful composed Surface into one Component when doing so hides independently modeled child Surfaces.

Names should reflect responsibility. Do not name an inner content Component as though it represents the complete surrounding composed Surface.

## Template and Slot

A `Template` declares zero or more Slots through `slotRefs`.

Slots represent reusable presentation positions.

They MUST NOT encode:

```text
Graph nodes
traversal
runtime instances
data binding
collection iteration
condition evaluation
business logic
```

Templates should not hard-code concrete Surface or Component targets.

Concrete assembly belongs to a `SurfaceRealization` through SlotBindings.

## SlotBinding

A `SlotBinding` connects one declared Slot to exactly one target:

```text
slotRef + targetSurfaceRef
```

or:

```text
slotRef + targetComponentRef
```

Never both.

Use `targetSurfaceRef` when the slotted element already has meaningful stable Surface identity.

Use `targetComponentRef` when the element is presentation-only and does not require independent Surface identity.

The `slotRef` MUST be declared by the Template used by that SurfaceRealization.

SlotBindings MUST NOT imply:

```text
graph traversal
state activation
transition validity
condition evaluation
form submission
execution order
composite containment
runtime lifecycle
data iteration
```

## Affordances in Slots

Before binding an affordance Surface:

1. confirm the Surface itself is justified;
2. confirm its `graphNodeRef` points to the actual experienced affordance;
3. identify the visible occurrence that owns it;
4. bind it within that owner's realization.

Do not create an affordance Surface merely because a Template needs a control.

If the visible control has no independent Surface identity, use a Component.

## Forms and editable states

Do not infer a separate visible action merely because Graph contains a transition between form-related States.

Typing, editing, correcting, selecting, or other within-state interaction does not automatically require a transition-backed Surface.

If one visible submit/continue interaction resolves through conditional alternatives, apply the conditional-outcome rules.

If an apparent Design System problem exists because Graph introduces an artificial transition for an interaction that requirements describe as remaining within one visible experience, report the Graph topology issue rather than inventing presentation semantics.

## Theme and TokenSource

Use `TokenSource` for an addressable token source, package, manifest, or token set.

Do not encode interoperable semantics for individual token names, values, aliases, CSS variables, inheritance, or calculations unless another active module defines them.

`Theme` identifies a design-system context through `tokenSourceRefs`.

Do not use `Theme` as:

```text
component inventory
template inventory
surface-realization registry
renderer
implementation manifest
```

Implementation resolvers MAY use stable node IDs to locate framework components, Storybook entries, source files, token files, or adapters.

Those mappings remain outside interoperable Design System semantics.

## Generation procedure

Use this order.

### 1. Inspect topology

Read the relevant:

```text
Journey
State / CompositeState
Transition
JourneyEntry
JourneyExit
ConditionalTransitionSet
```

Understand the experienced topology before creating Design System nodes.

### 2. Filter Surface candidates

For every existing or proposed Surface:

* verify stable visible meaning;
* reject mechanically created transition Surfaces;
* reject conditional-outcome Surfaces without independent visibility;
* reject structural-continuation Surfaces without independent visibility.

Remove rejected Surfaces before generating realizations.

### 3. Resolve occurrence ownership

For every nested visible affordance:

* find the nearest visible State/CompositeState occurrence that owns it;
* ensure that boundary has a Surface when stable composition requires one;
* compose the affordance there, not at an ancestor.

For multi-instance States, preserve the State -> Surface -> occurrence relationship.

### 4. Define minimal presentation vocabulary

Create only the Components, Templates, and Slots needed to realize the surviving Surfaces.

Do not duplicate Graph semantics in presentation vocabulary.

### 5. Realize Surfaces

Give each required Surface exactly one direct Component realization or one Template realization.

### 6. Add SlotBindings

Use `targetSurfaceRef` for independently modeled visible boundaries.

Use `targetComponentRef` for presentation-only content or controls.

### 7. Add Theme and TokenSource

Only when needed by the artifact.

### 8. Validate

Check references, cardinalities, vocabulary, Surface selection, occurrence ownership, and cross-layer semantics.

Report upstream modeling problems or expressivity gaps instead of inventing terms.

## Review order

Review whole documents in this order:

```text

→ Conditions and boundary transitions
→ Surface candidate validity
→ graphNodeRef alignment
→ occurrence ownership
→ Surface composition
→ SurfaceRealization
→ Templates and Slots
→ SlotBindings

```

Report findings by semantic severity, not file order.

Distinguish clearly between:

```text
Graph problem

Design System problem
expressivity gap
mechanical validation problem
```

Do not present an upstream Graph change as a Design System fix.

## Validation checklist

### Vocabulary

* Only active ED Design System terms are used.
* Graph nodes do not reference Design System artifacts.
* No stale or invented interoperable vocabulary was introduced.
* Theme uses only its active scope semantics.

### Surface selection

* Surfaces were not created mechanically for every Graph node.
* Every transition-backed Surface has independently justified visible identity.
* Transition labels were not treated as proof of controls.
* Conditional-outcome transitions were not turned into Surfaces without independent visibility.
* Structural continuation transitions were not materialized as duplicate actions.
* Unjustified existing Surfaces were removed rather than left unrealized.

### Graph/Surface alignment

* Every Surface exposes the Graph node that actually represents its visible experience.
* Local child affordances do not point to structurally related parent continuation transitions.
* One visible interaction is not duplicated across local and parent topology.

### Occurrence ownership

* Every child Surface is composed within the nearest visible occurrence that owns it.
* Item-local affordances are not bound directly into aggregate/page Surfaces.
* Multi-instance visible States retain a stable Surface boundary.
* Repeated visible States are not hidden inside opaque aggregate Components when their boundary matters.
* No per-runtime-occurrence Design System nodes were generated.
* No repetition, collection, cardinality, or instance-key semantics were invented in Design System.

### Realization

* Every required Surface has exactly one intended SurfaceRealization.
* Every realization references exactly one Surface.
* Every realization uses exactly one of `componentRef` or `templateRef`.
* `slotBindingRefs` occur only on Template-backed realizations.
* Components do not hide independently modeled child Surfaces that must remain composable.

### Slots and bindings

* Every bound Slot is declared by the realization's Template.
* Every SlotBinding has exactly one target.
* Every `targetSurfaceRef` references a Surface.
* Presentation-only elements use `targetComponentRef`.
* SlotBindings remain presentation-only.

### Modeling discipline

* Genuine user choices and conditional outcomes were distinguished.
* Forms did not acquire invented actions from topology alone.
* No `Command`, `Intent`, action kinds, flags, or transition subtypes were invented.
* No props, routes, URLs, CSS, runtime events, domain iteration, or business logic were added as interoperable Design System semantics.
* Upstream Graph/Surface issues were reported instead of hidden by presentation modeling.
* Expressivity gaps were reported explicitly.
